# Handoff: deploying DDP Inspector on Research Cloud

**To:** maintainers of `d3i-infra/researchcloud-ddp-transcribe` (the SRC provisioning component)
**From:** `~/src/ddp-inspector` (the app)
**Date:** 2026-07-08

## TL;DR

DDP Inspector is a small, read-only PHP web app that renders a **per-participant view of TikTok DDP extracts** so a researcher can validate donations. We want it served on a SURF Research Cloud workspace **behind the SRC-Nginx component with SRAM login** (CO-restricted), at the workspace FQDN.

The important thing to know up front: **your component is deliberately SSH-only** — no nginx, no SRAM `auth_request`, no PHP, no systemd, no web service anywhere today (`docs/catalog-item.md`: "No SRC-Nginx — the pipeline has no web UI; access is SSH only"). So this is **greenfield**: the inspector introduces the first web-serving capability. This doc gives you a concrete, convention-matching recipe plus the decisions we need from you.

Nothing here needs a GPU. The inspector reads the *same* DDP files the pipeline already stages, so co-locating it on the pipeline workspace is the simplest path.

---

## 1. What the app is

- **Vanilla PHP, stdlib only** — no Composer, no framework, no build step. Requires **PHP ≥ 8.1** (uses `array_is_list`).
- **Read-only.** It only *reads* DDP JSON files (and, optionally, a transcript tree). It never writes to data.
- **Server-rendered pages**, no client JS required. Three pages under `public/`: `index.php` (participant list + scope summary), `participant.php` (scope table + seeded-sampled sections), `transcript.php` (optional transcript + confidence, graceful "not transcribed yet").
- **Auth is entirely nginx's job.** The app has no login/session code; it relies on the SRC-Nginx `auth_request /validate` (SRAM) block to gate access to the CO.
- **Reverse-proxy-safe:** every link/asset path is relative, built from a configurable `base_path`, so it runs identically at `/` (local) or `/inspector` (behind the proxy).

Source layout (what needs to land on the workspace):
```
public/{index.php,participant.php,transcript.php,assets/style.css}
src/{Ddp.php,Stats.php,Sample.php,bootstrap.php}
config.php            # created on the workspace from config.php.example (NOT in git)
```
`tests/`, `docs/`, and `deploy/` are not needed at runtime.

## 2. Runtime configuration (`config.php`)

The app reads a single `config.php` returning an array. On the workspace it should be:

```php
<?php
return [
    // Read-only path to the TikTok DDP JSON files. Point at the SAME inbox the
    // pipeline uses (see §4): yoda backend -> ~/ddp-work/inbox ; volume backend -> <storage_path>/inbox
    'ddp_dir'         => '/home/<pipeline_user>/ddp-work/inbox',
    // Optional sharded transcript tree (<last-2-digits>/<id>.txt|.json). Point at the
    // pipeline's transcript output so transcripts light up as they are produced; or null.
    'transcripts_dir' => '/home/<pipeline_user>/ddp-work/transcripts',
    'default_n'       => 15,
    // MUST match the nginx location prefix (see §3). '' if served at root.
    'base_path'       => '/inspector',
];
```

`config.php` is gitignored (it carries an environment-specific, possibly sensitive path) — template it on the workspace, don't commit it.

## 3. Serving it (nginx + SRAM + PHP)

Two viable PHP models. **We recommend php-fpm** because it is self-supervising (its own systemd service), which matters on a persistent workspace and avoids hand-rolling a unit — but the `php -S`-under-systemd option mirrors the SRC "Web Apps via Nginx" demo playbook's `proxy_pass` shape more directly, so either is fine.

### Recommended: php-fpm + `fastcgi_pass`
An nginx location block for `/etc/nginx/app-location-conf.d/authentication.conf` (mirrors the SRC demo's `auth_request` SRAM guard; see `deploy/nginx-location.conf.example` in the inspector repo):
```nginx
location /inspector/ {
    error_page 401 = @custom_401;
    auth_request /validate;                       # SRAM login, CO members only
    auth_request_set $username $upstream_http_username;
    alias /opt/ddp-inspector/public/;
    index index.php;
    location ~ ^/inspector/(.+\.php)$ {
        include fastcgi_params;
        fastcgi_pass 127.0.0.1:9000;              # php-fpm
        fastcgi_param SCRIPT_FILENAME /opt/ddp-inspector/public/$1;
    }
}
```

### Alternative: `php -S` behind `proxy_pass` (closest to the demo playbook)
Run `php -S 127.0.0.1:8110 -t /opt/ddp-inspector/public` under a systemd unit, and `proxy_pass http://127.0.0.1:8110;` inside the same `auth_request`-guarded location — a near-verbatim swap of the demo's Node `web-app` block. A minimal unit:
```ini
# /etc/systemd/system/ddp-inspector.service — Generated by the researchcloud component; do not edit.
[Unit]
Description=DDP Inspector (read-only DDP viewer)
After=network.target
[Service]
User=<pipeline_user>
ExecStart=/usr/bin/php -S 127.0.0.1:8110 -t /opt/ddp-inspector/public
Restart=on-failure
[Install]
WantedBy=multi-user.target
```
Note: this introduces the first long-running service + systemd unit in the repo (which today states "No systemd: runs are operator-driven"). That's expected — a web viewer is a different beast from the batch pipeline.

**Firewall:** the app binds `127.0.0.1` only; no new inbound port beyond the 443 the SRC-Nginx component already exposes. Your current component opens only TCP 22 — the inspector requires the workspace to *also* include the **SRC-Nginx catalog component** ("Web Apps via Nginx" pattern), which is what provides `/validate` and the TLS front end.

## 4. Data wiring (reuse what you already stage)

The inspector needs no data of its own — point it at the pipeline's existing directories (from your `roles/preflight` facts):

| Inspector config | Pipeline path | Backend note |
|---|---|---|
| `ddp_dir` | `~/ddp-work/inbox` | yoda backend (pulled from the Yoda collection's `inbox`) |
| `ddp_dir` | `<storage_path>/inbox` | src-volume / research-drive backend |
| `transcripts_dir` | `~/ddp-work/transcripts` | boot-disk transcript output (optional) |

Because it's read-only, there is **no interaction with the pipeline's `flock`-serialized sync** — the inspector just reads whatever is on disk. It works whether or not any transcripts exist yet.

**Scale note:** it parses a participant's whole DDP file per request. Measured on the real pilot: a 9.6 MB / 90k-row donor renders in ~1.5–2 s at ~63 MB peak (well under a 128 MB limit). Fine for a single-researcher, auth-gated viewer.

## 5. How it fits your Ansible model

Suggested shape, matching your conventions (single play `vars:` block, `roles/<name>/tasks/main.yaml` + `templates/`, fully-qualified `ansible.builtin.*`, idempotent via `creates:`/`when: ... is changed`, cross-role facts from `preflight`, `| bool` coercion on SRC params, generated-file headers, Conventional Commits):

1. **New optional role `roles/inspector/`** — installs `php-fpm`/`php-cli` (apt), places the app at `/opt/ddp-inspector` (see §6 for how it gets there), templates `config.php` (Jinja, using `pipeline_home`/`work_dir`/`storage_path` facts and the `storage_backend` branch for `ddp_dir`), templates the nginx location conf into `/etc/nginx/app-location-conf.d/` and reloads nginx (or drops the systemd unit + enables it, for the `php -S` path).
2. **Gate it** in `deploy-ddp-transcribe.yaml`'s `roles:` list with `when: deploy_inspector | bool` so the pipeline-only workspaces are unaffected.
3. **New play vars** (pinned, lower_snake_case, prefixed): `deploy_inspector: false`, `inspector_src_ref` (if provisioning from git), `inspector_base_path: /inspector`, `inspector_port: 8110` (php -S path), `inspector_install_dir: /opt/ddp-inspector`.
4. **preflight assert** — fail-fast if `deploy_inspector | bool` but the SRC-Nginx component isn't present (e.g. `/etc/nginx/app-location-conf.d/` missing), with an actionable `fail_msg`, per your required-param pattern.
5. **`docs/catalog-item.md`** — add the parameter declarations and note that the inspector requires the SRC-Nginx component and (unlike the pipeline) exposes a web endpoint.
6. **Version pinning** — follow your two-pin model: the component Tag tracks this repo's `main`; add an `inspector_src_ref` param pinning the inspector's release the way `pipeline_git_ref` pins the pipeline.

## 6. Decisions we need from you

1. **Co-locate or separate workspace?** The inspector needs no GPU. Co-locating on the pipeline workspace (add the SRC-Nginx component to it) is simplest — it reads `~/ddp-work/inbox`/`transcripts` directly. A separate lightweight viewer workspace is cleaner isolation but must then mount/pull the same data. *Our lean: co-locate for the pilot.*
2. **How does the app get onto the workspace?** The inspector repo is **currently local-only (no git remote)**. Two options:
   - **Push it to your GitLab org** and have `roles/inspector/` `git clone` a pinned `inspector_src_ref` (matches your provisioning-from-git model). Needs a remote first.
   - **Vendor it** into `roles/inspector/files/` — the app is ~10 small text files with no build step, so `copy`/`synchronize` of a `files/ddp-inspector/` tree is entirely reasonable and removes the remote dependency. *Our lean: vendor for now, since it's tiny and has no build.*
3. **php-fpm vs `php -S`+systemd?** See §3. *Our lean: php-fpm (self-supervising).*
4. **Which `ddp_dir`?** Confirm the backend for the viewer workspace so the `config.php` template branches correctly (yoda → `~/ddp-work/inbox`; volume → `<storage_path>/inbox`).

Locally the same is reproducible with `./run-dev.sh` (`php -S 127.0.0.1:8110`) pointed at the DDP inbox.
